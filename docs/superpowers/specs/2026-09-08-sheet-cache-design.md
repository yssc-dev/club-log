# 구글시트 읽기 캐시 (RTDB) 설계

- 작성일: 2026-09-08
- 범위(1차): 테니스 3개 데이터셋. 축구·풋살은 어댑터 등록으로 확장(별도 스펙)
- 상태: 설계 확정 대기

## 1. 문제

앱 진입·탭 전환마다 Apps Script를 통해 구글시트를 전량 재조회한다.

- `tennisSync.js`에 캐시가 **전혀 없다.** `TennisDashboard` / `TennisLeague` /
  `TennisAnalyticsTab` 세 컴포넌트가 마운트마다 `getPlayerGames` + `getRoster` +
  `getLegacyRecords`를 **각각 독립적으로** 호출한다. 세 탭을 한 번씩 누르면
  Apps Script 왕복 **9회**, 매번 시트 전체 스캔.
- 풋살·축구도 같다. `TeamDashboard` / `PlayerAnalytics` / `DefenseTopCards` /
  `DualTeamTab` / `RecentFormTop3`가 각자 중복 호출한다.
- `appSync.js`의 5분 TTL 메모리 캐시는 **대회(tournament) 액션 6개에만** 걸려 있다.
- Apps Script 콜드스타트가 2~10초라 `AppSync.warmup()` 프리워밍까지 넣어둔 상태다.

**병목은 데이터 양이 아니라 `왕복 횟수 × 콜드스타트`다.**

## 2. 핵심 판단

"데이터가 바뀌었는지"를 **누구에게 묻느냐**가 설계를 가른다.

- Apps Script에 물으면 → 확인 자체가 콜드스타트 왕복(2~10초). 절약분을 도로 까먹는다.
- RTDB에 물으면 → 100~300ms.

따라서 **버전 마커를 RTDB에 두고, 평상시 Apps Script를 아예 호출하지 않는다.**
시트 직접 편집은 "거의 없다"는 확인을 받았으므로, 그 드문 경우를 위해
모든 사용자가 매 진입마다 콜드스타트를 지불하지 않는다 — 대신 수동 동기화 버튼을 둔다.

## 3. 구조 — 3층 캐시

새 모듈 `src/services/sheetCache.js`가 단일 진입점이다.
`tennisSync.js` / `appSync.js`는 **한 줄도 고치지 않는다** (L3 그대로 재사용).

```
get(dataset)
 ├ L1 메모리 히트?          → 즉시 반환 (네트워크 0)
 ├ L2 RTDB 읽기
 │   ├ version 있고 TTL 내?  → L1 채우고 반환 (~200ms)
 │   └ 없거나 만료/스키마변경 → ↓
 └ L3 시트 전량 조회 → L2 기록 → L1 채우고 반환
```

| 계층 | 적중 시점 | 비용 |
|---|---|---|
| L1 메모리 | 같은 세션 내 탭 전환 | 0 |
| L2 RTDB | 앱 첫 진입 | 100~300ms, Apps Script 0회 |
| L3 Sheets | 쓰기 직후 / 수동 동기화 / TTL 만료 | 전체조회 1회 |

### 3.1 in-flight 중복 제거 (필수)

`TennisDashboard`는 `Promise.all`로 3개를 동시에 쏜다. Promise 자체를 캐싱하지
않으면 L2도 똑같이 3번 두드린다. 진행 중 요청은 같은 Promise를 공유한다.

### 3.2 L1 메모리 TTL = 5분

`appSync.js`가 대회 액션에 쓰는 기존 관례와 같은 값으로 맞춘다. 탭 전환 폭풍은
5분 안에 끝나므로 목적을 100% 달성하고, 오래 열어둔 탭은 5분 뒤 L2를 다시 본다
(~200ms, 저렴). L1을 세션 내내 유지하면 8시간 열어둔 탭이 갱신을 영영 못 보는데,
이는 매 마운트마다 재조회하는 현재 동작 대비 **퇴행**이므로 허용하지 않는다.

### 3.3 컨텍스트와 데이터셋 이름

`team` / `sport`는 `AuthUtil.getStored()`의 `{ team, mode }`에서 얻는다
(`tennisSync._auth()`와 같은 출처). 데이터셋 이름은 다음 셋으로 고정한다:

`roster` | `playerGames` | `legacy`

## 4. RTDB 데이터 모델

기존 네임스페이스 관례(`games/{safeTeam}`, `settings/{safeTeam}`)를 따른다.

```
cache/{safeTeam}/{sport}/{dataset}/{shard}
  = { version, headers: [...], rows: [[...], [...]], count }

예: cache/몽피스/테니스/playerGames/all
    cache/몽피스/테니스/roster/all
    cache/몽피스/테니스/legacy/all
    cache/하버FC/축구/events/all      (5단계)
```

- `version` = 서버 타임스탬프(`{'.sv': 'timestamp'}`). "언제 시트에서 읽었나"가 곧 버전.
  별도 버전 카운터를 두지 않는다.
- `sport` 축을 처음부터 경로에 둔다 → 축구·풋살 확장이 **어댑터 등록 한 줄**이 된다.
- `shard`는 1차에 항상 `all`. 경로만 열어두고 구현하지 않는다(§9).
- 데이터셋을 쪼개는 이유: 회원 한 명 등록에 수천 행짜리 `playerGames`를 다시 읽을 이유가 없다.

### 4.1 배열형 저장 — 용량 (실측)

**캐시 노드는 팀별로 갈린다.** 스프레드시트는 마스터FC·하버FC·몽피스가 공유하지만
Apps Script가 요청 팀으로 필터해 내리므로, 노드 하나에는 한 팀 행만 들어간다.
용량은 시트 전체가 아니라 팀별로 따져야 한다.

2026-09-08 `export?format=csv&gid=` 로 전량 내려받아 실제 JSON 직렬화 바이트를 측정:

| 데이터셋 | 전체 행 | 팀 | 팀별 행 | 객체형 | 배열형 |
|---|---|---|---|---|---|
| 로그_이벤트 | 2,481 | 마스터FC | 1,279 | 444 KB | **221 KB** |
| | | 하버FC | 1,202 | 400 KB | **191 KB** |
| 로그_매치 | 691 | 마스터FC | 554 | 378 KB | **209 KB** |
| | | 하버FC | 137 | 87 KB | **46 KB** |
| 로그_선수경기 | 1,478 | 마스터FC | 948 | 367 KB | **153 KB** |
| | | 하버FC | 530 | 198 KB | **79 KB** |
| 로그_테니스선수경기 | 2,330 | 몽피스 | 2,330 | 1.42 MB | **635 KB** |

**한 팀이 자기 데이터셋을 전부 받는 총량 (배열형):**
마스터FC(풋살) 583 KB · 하버FC(축구) 316 KB · 몽피스(테니스) 635 KB.

RTDB 한도: **단일 쓰기 16 MB(SDK)** / 256 MB(REST), 저장 1 GB(Spark),
다운로드 10 GB/월(Spark). 현재 최대 노드(테니스 635 KB)가 쓰기 한도의 **4% 미만**이다.

배열형은 객체형의 41~55%. 로우데이터는 **전량 적재**되고 줄어드는 건 반복 키 이름뿐이다.

### 4.1.1 성장 여력 (실측 증가율)

`date` 열 기준 월평균 증가율과, 배열형 노드가 4 MB에 이르기까지 걸리는 기간:

| 데이터셋 / 팀 | 월 증가 | 행당 | 4 MB 도달 |
|---|---|---|---|
| 로그_테니스선수경기 / 몽피스 | 259행 | 279 B | **4.1년** |
| 로그_매치 / 마스터FC | 62행 | 387 B | 13.9년 |
| 로그_이벤트 / 마스터FC | 128행 | 177 B | 14.6년 |
| 로그_이벤트 / 하버FC | 134행 | 162 B | 15.4년 |
| 로그_선수경기 / 마스터FC | 105행 | 166 B | 19.3년 |
| 로그_선수경기 / 하버FC | 66행 | 153 B | 33.9년 |
| 로그_매치 / 하버FC | 17행 | 343 B | 58.8년 |

(로그_이벤트의 `date` 열은 `2026-08`과 `2026.8.` 형식이 섞여 있어 기간 산정이
로그_매치·선수경기보다 부정확하다. 증가율 자체는 매치 대비 비율로 타당하다.)

**16 MB 쓰기 한도는 실질적 제약이 아니다.** 먼저 부딪히는 것은 모바일
다운로드 체감이다(§9).

### 4.2 빈배열 함정 대응

Firebase는 빈 배열을 저장하지 않는다. `rows: []`를 쓰면 노드가 통째로 사라져
"캐시 미스"와 "진짜 0행"이 구분되지 않는다.

→ **히트 판정은 `rows`가 아니라 `version` 존재 여부로 한다.** `rows`는 `?? []`로 복원한다.
(`reconstructState`의 `normalizeSoccerMatch`가 같은 함정을 단일 지점에서 처리하는 것과 같은 원칙)

### 4.3 스키마 드리프트 자동 무효화

노드에 `headers`를 함께 저장하고, 읽을 때 현재 컬럼 상수
(`tennisSchema.js`의 `TENNIS_PLAYER_GAME_COLUMNS` 등)와 **배열 동등 비교**한다.
다르면 캐시 미스로 처리하고 시트에서 다시 읽는다.

배열형의 유일한 위험이 "컬럼이 바뀌면 인덱스로 오독"인데, 이 프로젝트에는 그 계열의
실제 사고 이력이 있다 — `fouls` 중간삽입(로그_선수경기 20↔21칸), 하버FC 선수기록
보관소에 크로바/고구마 열이 없어 실점을 고구마로 오독한 유령 ▲배지. 이 비교로 원천 차단한다.

## 5. 무효화 — "지우기"가 아니라 "재적재"

| 트리거 | 대상 | 주체 |
|---|---|---|
| 경기 마감 전송 | `playerGames` | 브라우저 `TennisApp` |
| 회원 upsert | `roster` | 브라우저 `TennisMembers` |
| 레거시 전적 쓰기 | `legacy` | 브라우저 |
| **자동 업로드 봇(매일 10:00 KST)** | `playerGames` | `scripts/tennisAutoUpload.mjs` |
| 설정 → 수동 동기화 | 전부 | 브라우저 |
| TTL 만료 (백스톱) | 해당 데이터셋 | 다음 읽기에서 자동 |

쓰기 직후 **시트를 다시 읽어 캐시를 통째로 교체**한다. 그냥 지우면 다음에 들어온
사람이 콜드스타트를 뒤집어쓴다. 재적재가 실패하면 **그때 노드를 삭제**해서 다음 읽기가
시트로 폴백하게 강등한다 — 낡은 캐시를 남기는 경우는 없다.

재적재는 **await 하되, 실패해도 원래 작업(마감·upsert)의 성공을 되돌리지 않는다.**
사용자는 이미 마감 전송을 기다리는 중이라 몇 초가 더 붙는 것이 fire-and-forget으로
띄우고 사용자가 화면을 떠나 캐시가 낡는 것보다 낫다. 실패는 `console.warn` +
노드 삭제로 끝내고, 마감 성공 alert은 그대로 뜬다.

### 5.1 자동 업로드 봇이 가장 중요한 경로다

현재 가장 흔한 쓰기 경로는 브라우저가 아니라 매일 10시의 봇이다. 봇이 캐시를 안
고치면 앱이 TTL 내내 어제 데이터를 보여준다.

- 봇은 이미 `rtdb()` REST 헬퍼와 `FIREBASE_DATABASE_URL`을 갖고 있어 새 의존성이 없다.
- 삽입 위치: `시트 전송 성공` **직후**, 기존 안전 불변식
  (`시트 전송 → meta 갱신 → finalized 쓰기 → active 삭제`)의 어느 단계도 캐시에 의존하지 않는다.
- **캐시 갱신 실패가 업로드를 실패시키면 안 된다.** try/catch로 감싸 실패 시 노드
  삭제 + 로그만 남기고 진행한다. `manualCheck` 플래그를 세우지 않는다(캐시는 파생 데이터).

## 6. 에러 처리 — 캐시는 절대 화면을 죽이지 않는다

| 실패 지점 | 동작 |
|---|---|
| L2 읽기 실패(네트워크·RTDB 장애) | 조용히 L3로 폴백 — **오늘과 동일한 동작** |
| L2 쓰기 실패 | 데이터는 이미 L3에서 받았으므로 그대로 반환. 다음 진입에 재시도 |
| L3 실패 | 기존 `_safeRead` 계약 그대로 — `[]` 반환 + `console.warn` |
| 재적재 실패 | 노드 **삭제**로 강등 → 다음 읽기가 시트 직행 |
| 노드 삭제까지 실패 | `version`을 `0`으로 덮어써 TTL 즉시 만료 (2단 방어) |

### 6.1 빈 결과는 캐싱하지 않는다

`tennisSync._safeRead`는 조회 실패를 `[]`로 삼킨다. 이 `[]`를 캐싱하면
**빈 캐시가 TTL 동안 고착되어 앱이 데이터를 잃은 것처럼 보인다.**

→ **L3 결과가 비어 있으면 L2에 쓰지 않는다.** "진짜 0행(신규 팀)"과 "조회 실패"를
구분할 방법이 없으므로 보수적으로 간다. 신규 팀은 첫 데이터가 생기는 순간 캐시가 채워진다.
비용은 데이터가 0인 동안 매번 시트를 읽는 것뿐이다.

## 7. 캐시를 쓰지 않는 읽기

| 호출 | 이유 |
|---|---|
| `TennisAttendeeSelector` → `getPlayerGames(date, date)` | "이 날짜에 이미 N판 기록됨" **중복 입력 정확성 가드**. 캐시가 뒤처지면 경고가 안 뜬다. 경기 시작 화면에서 하루 한 번 호출이라 시트 직행 비용이 무의미하다 |
| `TennisMembers` → `getRosterAdmin()` | `getRoster`와 **다른 데이터**(탈퇴·게스트 포함 + 행번호). 관리자 전용, 저빈도 |

`getRosterAdmin`은 캐시 대상이 아니지만 **upsert는 `roster` 캐시를 무효화해야 한다** —
두 뷰의 소스가 갈리는 지점이라 명시적으로 다룬다.

### 8.1 `safeTeam` 중복 제거

`_safeTeam`(팀명 → RTDB 안전 키)이 현재 `firebaseSync.js`와 `tennisAutoUpload.mjs`에
복사본으로 존재한다("한쪽을 고치면 다른 쪽도 고칠 것" 주석). 캐시가 세 번째 복사본이

하므로 브라우저·vite-node 양쪽에서 쓸 수 있다. 기존 두 곳은 이 모듈을 쓰도록 교체한다.
(작업 중인 코드의 targeted improvement — 범위를 넘는 리팩토링은 하지 않는다)

## 9. 샤딩 — 지금은 하지 않는다

경로에 `{shard}` 축만 열어두고 값은 항상 `all`.

**전환 트리거는 RTDB 한도가 아니라 모바일 다운로드 체감이다.** 16 MB 쓰기 한도까지는
테니스도 16년 이상 남았지만, 배열형 노드가 1.5 MB를 넘으면 4G에서 초기 렌더가
2~3초대로 늘어 캐시의 목적 자체를 깎는다.

- **전환 기준: 배열형 단일 노드 1.5 MB** (또는 초기 렌더 체감 지연이 관측될 때)
- 현재 최대인 테니스 635 KB → 월 72 KB 증가 → **약 1년 뒤 도달**
- 축구·풋살은 팀당 노드가 46~221 KB라 수년간 무관하다

전환 시 `shard=2026|2025|...` 연도 샤딩으로 간다. 리그·분석 탭이 이미 `effYear`로
연도를 거르고 있어(`availableYears` / `filterRowsByPeriod`) **그때는 오히려 평상시
다운로드가 줄어든다** — 기본값이 현재 연도이므로 한 해치만 받는다.

**지금 구현하는 것은 YAGNI**지만, 1년 내 필요해질 가능성이 높으므로 경로 축을 반드시
지금 뚫어둔다. 나중에 `shard` 결정 함수 하나를 교체하는 작업이 되게 한다.

## 10. 수동 동기화 UX

- 위치: `SettingsScreen`. 현재 관리자 도구 블록이 `isAdmin && !isTennis`로 테니스를
  제외하므로 **별도 블록**이 필요하다.
- 노출: **전원**. 비파괴적(시트를 읽어 캐시를 덮을 뿐)이고, 일반 회원이 "데이터가
  안 맞아요" 할 때 스스로 해결할 수 있는 편이 실용적이다. 관리자 전용 전환은 한 줄.
- 표시: `마지막 동기화: 2026-09-08 09:14 (12분 전)` + 데이터셋별 행수.
  캐시가 없으면 "아직 캐시 없음".
- 동작: 전 데이터셋을 시트에서 재적재 → 완료 후 행수 표시.
  기존 `recovering` / `recoverResult` 패턴을 그대로 따른다.
- 연타 방지: 진행 중 비활성화.

## 11. TTL

| 단계 | TTL | 이유 |
|---|---|---|
| 2단계(읽기 전환만) | 30분 | 무효화가 아직 없으므로 짧게 |
| 3단계 이후 | 12시간 | 모든 쓰기 경로가 재적재하므로 순수 백스톱 |

### 11.1 클럭 스큐

`version`은 RTDB 서버 타임스탬프이고 만료 판정은 클라이언트 `Date.now()`로 한다.
기기 시계가 틀어져도 안전하다 — 시계가 앞서면 캐시가 일찍 만료되어 시트를 더 자주
읽을 뿐(오늘 동작으로 수렴), 뒤처지면 `age`가 음수가 되어 신선으로 판정된다.
TTL은 백스톱일 뿐이고 모든 실제 갱신은 쓰기 경로가 담당하므로, 스큐가 데이터
정확성에 영향을 주지 않는다.

## 12. 테스트

순수 로직(계산·판정 함수를 부수효과에서 분리해 단위 테스트 가능하게 둔다):

1. 배열형 ↔ 객체형 왕복 — 헤더 순서대로 정확히 복원
2. `rows`가 없는 노드도 `version`이 있으면 **히트** (빈배열 함정)
3. 저장된 `headers`가 현재 컬럼 상수와 다르면 **미스**
4. TTL 만료 판정 경계값
5. L3 결과가 비면 L2에 쓰지 않는다
6. in-flight 중복 제거 — 동시 3회 호출이 fetcher를 **1회만** 호출
7. 어댑터 등록 커버리지 — 모든 데이터셋이 fetcher + columns 상수를 갖는다
   (`tennisSyncCoverage.test.js`의 커버리지 테스트 패턴을 따른다)
8. `safeTeam` 추출 후 기존 두 호출부와 동일한 결과

통합·렌더 (컴포넌트 렌더 검증 공백을 메우기 위해 기존 render 테스트를 확장):

9. `tennisDashboard.render.test.jsx` / `tennisAnalyticsTab.render.test.jsx` 모킹
   대상을 `SheetCache`로 교체 — 렌더 결과가 전환 전과 동일
10. L2 실패 시 L3 폴백으로 정상 렌더
11. 마감 성공 후 `refresh('playerGames')`가 호출된다

## 13. 적용 순서

각 단계가 독립 배포·독립 롤백 가능하다.

1. **캐시 모듈 + `rtdbPath.js` + 단위 테스트.** 아무도 안 쓴다. 배포해도 동작 변화 0.
   여기서 Apps Script 경유 **실측 행수**를 재고 §4.1 표를 갱신한다.
2. **읽기 경로 전환** — 3개 탭 + `TennisApp` 로스터. 체감 개선이 여기서 나온다. TTL 30분.
3. **쓰기 경로 무효화** — 마감 / 회원 upsert / 봇. TTL 12시간으로 상향.
4. **설정 수동 동기화 버튼.**
5. **축구·풋살 어댑터 등록** — 별도 스펙. 1~4단계 실측 후.

## 14. 롤백

`sheetCache.js`에 `DISABLED` 상수 하나. `true`면 모든 호출이 L3 직행 — 오늘과 동일한 동작.
빌드+push로 GitHub Actions가 자동 배포하므로 한 줄 변경으로 되돌릴 수 있다.

## 15. 범위 밖

- 풋살·축구 어댑터 (5단계, 별도 스펙)
- `onValue` 실시간 구독. 대시보드를 보는 동안 남이 마감하는 상황은 드물고,
  `firebaseSyncDiff`와 무관한 새 구독 경로가 하나 더 생긴다. 마감한 본인 화면은
  L1이 비워져 즉시 갱신되고, 다른 사람은 다음 진입에 반영된다. 구조상 나중에 얹을 수 있다.
- 연도 샤딩 (§9)
- 쓰기 경로 캐싱. 이 스펙은 **읽기 전용**이다.
- RTDB 보안 규칙 변경. 캐시의 노출 수준은 현재와 실질적으로 같다 — 경기 상태에 이미
  선수 이름이 들어 있고, `getTennisRoster`는 서버가 생년월일을 제외하고 내린다.
