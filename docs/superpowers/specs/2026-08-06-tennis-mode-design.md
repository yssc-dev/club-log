# 테니스 종목 추가 설계

작성일: 2026-08-06
대상 저장소: `footsal_webapp`

## 1. 배경

풋살·축구를 운영 중인 이 앱에 세 번째 종목으로 테니스를 추가한다. 대상 클럽은 **아침의 평화 테니스 클럽**(약칭 몽피스, Morning Peace Tennis Club, 창단 2024.07)이며 회원 16명 + 비회원 용병이 참여한다. 몇 주 내 실경기 기록이 목표다.

테니스는 구기 종목과 공유하는 기록 필드가 사실상 없다. 골·어시스트·자책골·실점·클린시트·키퍼가 전부 무의미하고, 대신 세트·게임·타이브레이크·서브에이스·더블폴트가 필요하다. 또한 회원마다 **등급**과 **리그**라는 두 축이 있고 이것이 랭킹 포인트에 직접 들어간다.

## 2. 접근 방식

**전용 시트 + 전용 앱.** 테니스 전용 시트 3종과 `TennisApp`을 신설하고, 기존 풋살/축구 코드에는 새 분기만 더한다.

대안이었던 두 가지를 기각한 이유:

- **기존 통합 스키마 확장**: `로그_매치`는 테니스와 그럭저럭 맞지만 `로그_선수경기`가 문제다. 20칸이 구기 전용이고, 이 시트의 읽기는 시트 헤더가 아니라 하드코딩된 `RAW_PLAYER_GAMES_HEADERS` 순서 매핑이라 컬럼을 늘리면 풋살/축구 읽기 경로를 건드리게 된다.
- **공통 셸 추출 후 얹기**: 장기적으로 옳지만 실사용 중인 풋살/축구를 반드시 수정해야 한다. 이 저장소엔 RTL 하네스가 없어 렌더 크래시를 build도 vitest도 잡지 못한다. 몇 주 시한 안에 감수할 위험이 아니다. 이 방향은 `club-platform`에서 다룬다.

## 3. 범위

### 1차 (이번 구현)

기록 파이프라인 전체 + 기본 랭킹.

- 테니스 회원 명부 적재
- 경기 생성 → 참석자 선택 → 라운드/코트 구성 → 점수 기록 → 경기 마감 → 시트 전송
- 단식 승률 랭킹(흑기사/흑장미 구분 포함), 개인별 전적 요약

### 2차

- 파트너 케미, 상대전적, 월별 폼 추이 그래프
- 타이브레이크 승률, 서브에이스/더블폴트 분석, 베이글 랭킹
- 포인트 랭킹 (산식 확정 후), 연령대 분석

**1차에서 로그 스키마는 2차 지표를 모두 계산할 수 있도록 완성한다.** 2차에 시트 마이그레이션이 발생하면 안 된다.

## 4. 도메인 모델

### 4.1 경기 형식

- 한 **판(match)** = 1세트 또는 3세트(3판 2선승). **코트마다 선택**하며 기본값은 **1세트**.
- 한 **세트** = 6게임 선취.
- 세트가 **5:5에 도달하면 타이브레이크**로 전환. 7점 선취(노애드).
- **단식/복식은 명시적 토글로 정한다.** 토글 값에 따라 편당 슬롯이 1개(단식) 또는 2개(복식)로 열리고, 열린 만큼만 채울 수 있다. 인원으로 역추론하지 않는다.
- **라운드를 추가하면 코트 1개가 함께 생긴다.** 더 필요하면 코트 목록 아래 `[+ 코트]`로 늘린다. 3코트 이상도 가능하며 **코트 수에 상한을 두지 않는다.**
- **새 코트의 기본값은 단식 · 1세트다.**
- 하루 판 수, 라운드당 코트 수, 라운드 수에 상한이 없다. 코트마다 단복식과 세트 수가 독립이다.

### 4.2 두 개의 축

| 축 | 값 | 결정 방식 | 저장 |
|---|---|---|---|
| **등급** | 초보자 / 동배 / 은배 / 금배 | 관리자가 명부에서 수동 지정. 은배리그에서 메달을 따야 은배가 된다. | 경기일 스냅샷 |
| **리그** | 흑기사(BK) / 흑장미(BR) | **단식 승률** 순위 1~8위가 흑기사, 9~16위가 흑장미. 유동적이며 강등을 "버스 탄다"고 부른다. | 저장하지 않고 파생 |

**리그를 저장하지 않는 이유.** 승률 기반 유동값이라 명부에 두면 반드시 실제 순위와 어긋난다. 반면 "경기일 직전까지의 시즌 누적 단식 승률"이라는 정의는 로그를 날짜순으로 재생하면 결정적으로 복원된다. 저장하면 오히려 마감 순서에 따라 틀어진다.

**등급을 스냅샷하는 이유.** 관리자가 명부를 고치면 과거 경기의 포인트가 소급되어 흔들린다. 경기일 시점 값을 로그에 박아야 고정된다.

### 4.3 시점 고정 규칙

**등급과 승률 모두 경기일 이전 값을 그대로 쓴다.** 8/6이 경기일이면 8/5까지의 값으로 그날 전 판을 판정한다. 8/6 당일에 승률이 어떻게 변하든 그날 안에서는 반영하지 않는다.

이로부터 따라오는 것:

- 오전에 이겨서 오후에 흑기사로 올라가는 일이 없다. 그날 하루는 전 판이 같은 리그 배치를 쓴다.
- 리그 계산이 판마다가 아니라 **경기일당 1회**로 끝난다. 마감 순서나 판 순서가 꼬여도 포인트가 흔들리지 않는다.

**경계 조건:**

- 참여 인원이 16명이 아니면 **상위 절반**을 흑기사로 한다.
- 시즌 초 승률 데이터가 없으면 **전원 동일 리그**로 시작하고, 단식 기록이 쌓이는 대로 다음 경기일부터 갈라진다.
- 명부의 `시즌시작순위` 컬럼에 값이 있으면 그것으로 첫 배치를 한다. 2026 기록지를 나중에 확보하면 코드 수정 없이 시트만 채우면 된다.

### 4.4 리그(대회) 성립 조건

| | 이름 | 성립 조건 |
|---|---|---|
| 단식 | 길로틴리그 | 양쪽 다 몽피스 회원일 때만 |
| 복식 | 투몽리그 | 4명 중 회원이 3명 이상일 때 |

성립하지 않는 판도 로그에는 남긴다. 케미·상대전적에는 쓰고 **순위표에서만** 제외한다.

### 4.5 랭킹

| | 순위 기준 | 포인트 |
|---|---|---|
| 단식 (길로틴) | 승률 | 적립 |
| 복식 (투몽) | 페어 조합 승패 → 세트 득실 | 없음 |

**포인트는 단식 전용이며 조건별로 누적된다.**

| 조건 | 점수 |
|---|---|
| 기본 승리 | 1 |
| 동일 리그에서 승률 낮은 쪽이 이김 | +2 |
| 흑장미가 흑기사를 이김 | +3 |
| 동배가 은배를 이김 | +5 |

"동일 리그 승률 역전(+2)"과 "리그 역전(+3)"은 상호 배타적이다. 최대는 1+3+5 = 9점이다.

순위 자체는 승률로 매기고 포인트는 별도로 적립한다.

### 4.6 베이글

세트 스코어가 **6:0이면 그 세트마다** 진 쪽에 `bagels_taken +1`, 이긴 쪽에 `bagels_given +1`. 3세트 경기에서 6-0, 3-6, 6-0이면 진 사람이 2개를 받는다.

랭킹 포인트에는 들어가지 않는다. "굴욕 랭킹" 재미 카드 전용이다.

### 4.7 용병과 출석

- 용병(비회원)은 이름 자유 입력으로 그 자리에서 추가한다. 반복 참여자는 명부에 등록해두면 오타를 막는다.
- 용병 기록은 로그에 남기고 **리그 순위표에서만** 제외한다.
- **출석은 실제로 뛴 사람만** 집계한다. 참석했으나 한 판도 안 뛴 경우는 다루지 않는다.
- **경기 도중 선수 추가를 지원한다.** 참석자 목록을 경기 생성 시점에 잠그지 않는다. 중도 이탈은 다루지 않는다.

## 5. 데이터 스키마

기존 `로그_이벤트` / `로그_선수경기` / `로그_매치`는 건드리지 않는다.

### 5.1 `테니스_회원명부`

| 컬럼 | 설명 |
|---|---|
| 팀이름 | `회원인증` 시트의 팀이름과 일치 |
| 이름 | 고유 키 |
| 닉네임 | 표시용 |
| 생년월일 | 연령대 분석용 (2차) |
| 등급 | 초보자 / 동배 / 은배 / 금배 |
| 상태 | 활동 / 휴면 / 탈퇴 |
| 시즌시작순위 | 비어 있으면 전원 동일 리그로 시작 |
| 가입일 | |
| 비고 | |

리그(흑기사/흑장미) 컬럼은 두지 않는다. 4.2 참조.

### 5.2 `로그_테니스매치` — 판마다 1행

```
team · sport · season · date · game_id
round_idx · court_id · match_idx · match_id
format(단식|복식) · best_of(1|3)
side_a_json · side_b_json
sets_json · sets_a · sets_b · games_a · games_b · winner(A|B)
league(길로틴|투몽|미반영) · input_time
```

- `match_id` 포맷: `R{round}_C{court}` (예: `R2_C1`). `match_idx`는 그날 판의 일련번호다.
- `sets_json` 예: `[{"a":6,"b":3},{"a":4,"b":6},{"a":6,"b":5,"tbA":7,"tbB":4}]`
- 세트가 5:5에서 타이브레이크로 가면 승자가 6번째 게임을 가져가 **게임 스코어는 6:5**가 되고, 타이브레이크 점수는 `tbA`/`tbB`에 따로 담는다. 화면에는 `6:5 (7-4)`로 표시한다.
- `sets_a`/`sets_b`는 **획득 세트 수**, `games_a`/`games_b`는 **전 세트 게임 합계**다.
- **`side_a_json`은 항상 화면 왼쪽 팀이다.** 6.3 참조.

### 5.3 `로그_테니스선수경기` — 선수 × 판마다 1행

개인 지표의 진실 소스.

```
team · sport · season · date · game_id · match_id · round_idx · court_id
player · is_guest · side(A|B) · format · best_of
partner · opponents_json · result(승|패)
sets_won · sets_lost · games_won · games_lost
tb_played · tb_won · aces · double_faults
bagels_taken · bagels_given
grade_at_date · league(길로틴|투몽|미반영) · input_time
```

- `partner`는 복식일 때만 채운다.
- `grade_at_date`는 (경기일 × 선수)당 하나인 값이라 같은 날 행에서 모두 같아야 한다.
- 복식 행에도 `grade_at_date`를 기록한다. 포인트에는 안 쓰지만 "등급별 조합 승률" 같은 2차 분석에 필요하고, 나중에 넣으면 과거 로그를 채울 수 없다.

### 5.4 지표 요구사항 → 컬럼 매핑

1차 스키마가 2차 지표를 모두 감당하는지 확인한다.

| 요구사항 | 계산 근거 |
|---|---|
| 승률 | `result` (단식/복식/전체 분리) |
| 시즌별·월별 성적 추이 | `season`, `date` |
| 상대전적 | `opponents_json` |
| 랭킹 | 승률 + 포인트 파생 (4.5) |
| 서브에이스 | `aces` / 판 수 |
| 더블폴트 | `double_faults` / 판 수 |
| 타이브레이크 승률 | `tb_won` / `tb_played` |
| 파트너 조합별 승률 | `partner` |
| 출석 | `date` distinct count |
| 베이글 | `bagels_taken`, `bagels_given` |
| 언더독 격파 횟수 | 승률 역전 승 카운트 (로그 재생으로 파생) |
| 연령대 분석 | 명부 `생년월일` |

## 6. 진행 중 상태와 화면

### 6.1 상태 모델 (Firebase RTDB)

```
{
  gameId, team, sport: '테니스', gameDate, season, phase,
  attendees: [name...],       // 경기 중 추가 가능
  guests:    [name...],
  rounds: [ { roundIdx, courts: [Court] } ]
}

Court = {
  courtId, format, bestOf,
  sideA: [name], sideB: [name],
  sets: [ { a, b, tbA, tbB, done } ],
  currentSet, status: 'ready'|'playing'|'done',
  stats: { [name]: { aces, df } },
  undoStack: [action...]
}
```

기존 실시간 동기화 아키텍처에서 확인된 함정 세 가지를 설계에 반영한다.

- **빈 배열 누락**: Firebase는 빈 배열을 저장하지 않아 동기화 후 `rounds`/`courts`/`sets`/`sideA` 등이 `undefined`가 된다. 호출부에서 땜질하지 않고 `normalizeTennisMatch()` **단일 지점**에서 복원한다.
- **자식 컴포넌트의 `useState(prop)` 금지**: 코트 카드는 로컬 state로 점수를 들지 않고 리듀서 dispatch만 한다.
- **배열 index 의존 금지**: 코트/라운드는 `roundIdx`/`courtId` 논리 키로 매칭한다.

### 6.2 플로우

```
대시보드 [경기 추가]
   → 날짜 + 참석자 선택 (명부 체크 · [+용병])
   → 라운드 1 + 코트 1 자동 생성
        단식/복식 토글 → 칩 탭으로 배치 → 세트 수(1/3) → [시작]
        → ▲ 증분 · 에이스/DF · [되돌리기] · [세트 종료] → 판 종료
        (코트가 더 필요하면 목록 아래 [+ 코트])
   → [라운드 추가] (코트 1개와 함께 생성) · ◀▶ 라운드 이동
   → [경기 마감] → 시트 2종 전송
```

### 6.3 화면 규칙

**코트 배치는 세로 스택.** 라운드에는 코트 1개가 이미 놓여 있고, 진행 중인 코트만 펼치고 끝난 코트는 한 줄 요약으로 접는다. `[+ 코트]`가 목록 맨 아래에 붙는다. 코트 수가 유동적인 모델과 맞고, 여러 사람이 각자 코트를 기록할 때 남의 코트가 스크롤만으로 보인다.

**코트 설정은 토글이 먼저다.** 단식/복식 토글이 편당 슬롯 수를 결정한다 — 단식이면 좌우 1칸씩, 복식이면 2칸씩 열린다. 세트 수는 1세트가 기본이고 3세트를 고를 수 있다. 배치 도중 토글을 바꾸면 슬롯이 다시 열리며, 줄어드는 쪽에서 넘치는 인원은 칩 목록으로 되돌린다.

**선수 담기는 탭 순서 자동 배치.** 칩을 연달아 탭하면 열린 슬롯을 왼쪽 → 오른쪽 순서로 채운다. 복식은 탭 4번, 단식은 2번. 어긋나면 칩의 `×`로 빼거나 `⇄ 좌우 교체`로 편을 통째 바꾼다. 이미 다른 코트에 앉은 사람은 잠긴다.

**좌우 축을 끝까지 유지한다.** 이름·스코어·▲ 버튼·에이스/DF를 한 세로줄에 세우고, 왼쪽 ▲는 왼쪽 팀만 올린다. 배치 → 진행 → 완료 요약 → 시트 로그까지 **A편 = 왼쪽**으로 고정한다. `side_a_json`이 늘 왼쪽 팀이면 기록을 다시 열어도 화면과 데이터가 어긋나지 않는다.

### 6.4 코트 설정 잠금과 복구

**`[시작]`을 누르면 단식/복식 토글과 세트 수가 잠긴다.** 도중에 바뀌면 이미 기록한 점수의 의미가 달라지기 때문이다.

잘못 세팅한 경우를 위해 진행 카드 구석에 **`[설정 수정]`**을 둔다. 동작은 변경 종류에 따라 갈린다.

| 변경 | 동작 |
|---|---|
| **1세트 → 3세트** | **점수를 유지한 채 즉시 허용.** 이미 친 세트는 그대로 두고 세트 수만 늘린다. 현장에서 "한 세트 더 치자"가 되는 상황이 잦아 예외로 둔다. |
| 3세트 → 1세트 | 점수 초기화 후 배치 화면 |
| 단식 ↔ 복식 | 점수 초기화 후 배치 화면 |
| 선수 교체 | 점수 초기화 후 배치 화면 |

초기화가 필요한 변경이라도 **아직 0:0이고 기록된 세트가 없으면 경고 없이** 배치 화면으로 돌아간다. 기록된 점수가 있을 때만 "기록된 점수가 지워집니다" 확인을 받는다.

**코트 삭제는 `배치 중`(ready) 상태에서만 노출한다.** 시작한 코트를 지우려면 `[설정 수정]`으로 배치 화면에 돌아간 뒤 삭제한다. 진행 중인 카드에 삭제 버튼을 두면 오터치 한 번으로 기록이 날아간다.

이미 종료된 판은 `[설정 수정]`이 아니라 **완료 카드를 탭해 펼치는 경로**로 고친다. 그 안에서의 변경에도 위 표와 같은 규칙을 적용하며, 세트를 늘리면 승패를 다시 계산한다.

### 6.5 되돌리기

증분 버튼은 누르는 즉시 반영·동기화되므로 오입력 복구 경로가 필요하다. **코트마다 액션 스택을 따로 쌓는다** — 코트1의 되돌리기가 코트2를 건드리면 안 된다.

한 스택에 들어가는 것: 게임 +1, 에이스 +1, 더블폴트 +1, 세트 종료. 마지막 동작부터 순서대로, 몇 번이든 연속 취소할 수 있다.

**판 종료는 스택에 넣지 않는다.** 완료 카드를 탭해 펼쳐서 수정하는 별도 경로로 다룬다.

### 7.2 기존 파일 수정 (4곳)

넷 다 **기존 분기를 고치는 게 아니라 새 분기를 더하는** 형태다. 풋살/축구 경로는 그대로 지나간다.

| 파일 | 수정 |
|---|---|
| `src/Root.jsx` | 라우팅 한 줄 — `mode === '테니스' → TennisApp` |
| `src/components/dashboard/TeamDashboard.jsx` | 메인 탭 구성 분기 + 본문을 `TennisTabs`로 위임 + 풋살/축구 전용 fetch guard |
| `src/config/settings.js` | `SPORT_DEFAULTS`/`PRESETS`에 테니스 추가. **`isLegacyFormat`도 함께 수정** — 현재는 `풋살`/`축구` 키가 없으면 레거시로 판정해서, 테니스만 있는 팀 설정이 매번 마이그레이션 대상이 된다. |
| `apps-script/Code.js` | action 분기 추가 + 상단 changelog 기록 |

### 7.3 대시보드 셸 공유

헤더(팀명·이름·관리자 배지·테마/설정/메뉴)와 종목 칩은 **그대로 공유한다.** 종목 칩은 `teamEntries.map`으로 그려지므로 `회원인증` 시트에 `mode=테니스` 행만 넣으면 코드 수정 없이 생긴다.

그 아래 메인 탭 바와 본문만 종목별로 분기한다. 테니스에는 대회 탭이 없다.

| 탭 | 1차 | 2차 |
|---|---|---|
| 대시보드 | 단식 승률 랭킹 + 흑기사/흑장미 구분 | 포인트 랭킹, 베이글 등 재미 카드 |
| 개인기록 | 개인별 전적 요약 | 월별 폼 그래프 |
| 분석 | 준비 중 | 케미 · 상대전적 · 추이 · 타이브레이크 · 에이스/DF |
| 경기관리 | 경기 추가 · 이어하기 · 기록 목록 | — |

## 8. 마감과 실패 처리

기존 마감 플로우 정책을 승계한다.

- `로그_테니스매치`와 `로그_테니스선수경기`를 **병렬 전송**한다.
- **둘 중 하나라도 실패하면 미확정 상태를 유지**해 재시도할 수 있게 한다.
- 미완료 코트가 남아 있으면 마감 전에 경고한다. 그대로 진행하면 **미완료 판은 전송하지 않고 버린다.** 승자가 정해지지 않은 판을 로그에 넣으면 승률이 오염되기 때문이다. 경고 문구에 버려질 코트를 명시한다.
- 재마감 중복은 자동 멱등화하지 않는다. 기존 정책대로 시트에서 수동 정리한다.

## 9. 검증 전략

순수 함수 유닛 테스트가 주력이다.

| 대상 | 케이스 |
|---|---|
| `tennisScoring` | 세트 승자 판정, 5:5 타이브레이크 전환, 7점 선취, 베이글 판정 |
| `normalizeTennisMatch` | `rounds`/`courts`/`sets`/`sideA`가 `undefined`로 들어올 때 복원 |
| `leagueDerivation` | 경기일 경계(당일 결과 미반영), 인원 ≠ 16, 시즌 초 데이터 없음, 시드값 존재 |
| `rankPoints` | 규칙 누적, +2와 +3의 상호 배타, 복식 제외 |
| `tennisRowBuilders` | 컬럼 순서, 용병 `is_guest`, 리그 성립 판정 |
| `useTennisReducer` | 증분, 되돌리기(연속), 세트 종료, 판 종료, 코트 추가, 라운드 추가, 경기 중 선수 추가 |
| 설정 잠금/복구 | 시작 후 토글 잠김, 1→3세트는 점수 유지, 3→1·단복식 변경은 초기화, 0:0이면 경고 생략, 코트 삭제는 ready에서만 |

**렌더 검증 공백을 전제로 한다.** 이 저장소엔 RTL 하네스가 없어 build도 vitest도 렌더 크래시(TDZ 등)를 잡지 못한다. 화면 작업 후 **브라우저 스모크를 필수 단계로** 플랜에 박는다.

## 10. 미확정 항목

| 항목 | 상태 | 처리 |
|---|---|---|
