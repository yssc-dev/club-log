# 테니스 2차 설계 — 분석 지표 + 레거시 데이터 통합

- 날짜: 2026-08-10
- 대상: 몽피스(모닝 피스 테니스 클럽)
- 선행: `2026-08-06-tennis-mode-design.md`(1차 스펙), `2026-08-06-tennis-mode-phase1.md`(1차 플랜)

## 1. 배경과 목표

1차에서 기록 파이프라인(명부→경기→점수→마감→시트)과 단식 승률 랭킹까지 완료했다. 2차는 두 축이다.

1. **레거시 데이터 통합** — 클럽이 스프레드시트("모닝피스클럽")로 관리해 온 2024~2026.7 기록을 앱으로 들여온다.
2. **분석 지표 화면** — 개인성적(승패/승률/포인트랭킹), 파트너 케미, 상대전적, 월별 흐름 그래프, 타이브레이크 승률, 에이스/더블폴트, 베이글. 복식과 단식은 분리해서 본다.

## 3. 소스 데이터 (모닝피스클럽 스프레드시트)

- 스프레드시트 ID는 **커밋하지 않는다**(이 리포는 public) — 유저가 보유하고, 마이그레이션 스크립트는 환경변수/CLI 인자로 받는다.
- 읽기는 `export?format=csv&gid=` 또는 xlsx export 사용(gviz CSV는 열 타입 강제로 값 유실 — 기존 메모리 규칙).

| 탭 | 내용 | 용도 |
|---|---|---|
| `2024시즌 전적`, `2025시즌 전적` | 선수별 복식+단식 승/패/승률 집계 | 레거시전적 적재 소스 |
| `단식리그 길로틴 전적(1그룹)/(2그룹)` | 2025 길로틴 최종 순위 | 시즌시작순위 소스 |
| `1월~7월 복식 기록` (2026) | 판별 로우: 날짜, A_P1, A_P2, B_P1, B_P2, A점수, B점수 | 로그 마이그레이션 소스 |
| `N월 전적(2026)`, `2026시즌 전적`, `통산 전적` | 집계(수식) | 적재하지 않음 — 검산 대조용 |

2026 복식 판수: 1월 73 / 2월 80 / 3월 97 / 4월 76 / 5월 57 / 6월 59 / 7월 57 = **합계 499판**.

시즌시작순위 기입 순서는 소스 시트 `단식리그 길로틴 전적(1그룹)/(2그룹)` 탭의 최종 순위를 1그룹→2그룹으로 이어붙인 16명(실명 나열은 커밋하지 않는다 — public 리포). 순위 명단에 없는 회원은 말번으로 이어붙인다. 축약명 중 **'원택'과 '윤택'은 별개 인물**(통산 전적 탭에 각각 존재) — 매핑 시 혼동 금지.

## 4. 데이터 모델

### 4.1 새 시트 `테니스_레거시전적`

컬럼: `team, sport, season, format, player, wins, losses`

- 행 단위: 시즌×종목(단식/복식)×선수. 2024 복식 12명+단식 12명, 2025 복식 16명+단식 16명 ≈ 56행.
- player는 **회원명부 실명**으로 변환해 적재.
- 헤더 배열은 `src/utils/tennis/tennisSchema.js` ↔ `apps-script/Code.js`에 **1:1 동일 순서로 추가**(기존 규칙). Apps Script 상단 changelog에 기록. Apps Script 반영은 유저 수동.
- 통산 전적은 시트에 저장하지 않고 앱이 "레거시전적 + 로그 실계산" 합산으로 만든다.

### 4.2 2026 복식 마이그레이션 → `로그_테니스매치` + `로그_테니스선수경기`

일회성 vite-node 스크립트. 기존 Apps Script append 엔드포인트 재사용, 배치 전송.

변환 규칙:

- **게임/매치 구성**: 날짜당 game 1개(`game_id`에 `legacy_` 접두어). round_idx=**그날 판 순번**, court_id=1로 채워 match_id(`R{n}_C1`)가 그날 안에서 판별로 유일해지게 한다(같은 날 모든 판이 R1_C1을 공유하면 매치행↔선수경기행 조인이 카테시안이 된다). match_idx=판 순번.
- **필드 고정값**: season=2026, format=복식, best_of=1.
- **league는 고정값이 아니다**: 판마다 `tennisRowBuilders.js:determineCompetition(format, sideA, sideB, memberSet)`으로 판정한다(회원 3인 미만 판은 `미반영`). 1차 스펙 §4.4 규칙 — 미반영 판도 로그에는 남기고, 케미·상대전적에는 쓰되 **순위표에서만 제외**된다. `league=투몽`을 전 판에 박으면 게스트 낀 판이 순위 집계에 오염된다.
- **이름 매핑**: 축약명→회원명부 실명 매핑 테이블(스크립트 내 명시). 명부에 없는 이름(동현·두리·교류전·게스트 등)은 `is_guest=true`, 이름 원문 보존.
- **스코어 복원 — 기존 계산기를 재사용한다(재발명 금지)**: 판마다 합성 set 객체 `{ a, b, tbA, tbB }`를 구성해 `tennisScoring.js:summarizeCourt`로 sets/games/winner/tb/bagel을 산출하고, `sets_json`은 `tennisRowBuilders.js:serializeSets`의 표준 포맷(`[{"a":6,"b":5,"tbA":…,"tbB":…}]` — 배열-of-배열 아님)으로 직렬화한다.
  - **6-5 / 5-6 → 타이브레이크 소급**: 클럽 규칙(5:5 타이브레이크)상 TB 경기. 소스에 TB 점수가 없으므로 승자 측 `tbA(또는 tbB)=1`을 **발생 표식(sentinel)**으로 넣는다 — `summarizeCourt`가 TB를 tbA/tbB>0으로만 감지하므로 표식이 없으면 매치행에서 TB가 소실된다. 값 1은 점수가 아니라 표식임을 스펙·코드 주석에 명기.
  - **6-0 / 0-6 → 베이글 소급**: `summarizeCourt`가 자동 산출(bagels_given/taken).
  - **에이스/더블폴트는 빈값으로 적재**(0 금지). 분석에서 "미기록"으로 구분한다. **`buildTennisPlayerGameRows`는 재사용 금지** — `aces: st.aces || 0` 패턴이라 빈값이 0으로 덮인다. 선수경기 행은 독립 조립(단, summarizeCourt 결과를 복사).
- **검증 게이트**: dry-run 리포트(이름 매핑 표, 게스트 목록, league 판정 분포(투몽/미반영), 월별 판수 검산, 스코어 이상치)를 유저 승인받은 뒤에만 실제 적재. **전량 검증 통과 시에만 적재, 부분 적재 없음.**
- **적재 preflight**: 인증 `team`이 비어 있지 않음을 단언하고 시작한다 — Apps Script `_checkTeamAccess`는 빈 `requestTeam`을 무조건 통과시키므로(Code.js:249), 미인증 환경에서 돌리면 팀 격리를 우회한다. 참고: `writeTennis*` 액션은 ADMIN_ACTIONS에 없다 — 일반 회원 마감 플로우가 쓰는 액션이라 의도된 것이며, 대량 쓰기의 유일한 방어벽이 이 스크립트의 dry-run 게이트라는 가정을 여기 명시해 둔다.
- **재실행 가드**: 로그에 `legacy_` game_id가 이미 있으면 중단. 재적재는 유저가 수동으로 해당 행 삭제 후 재실행(풋살 재마감 관행과 동일, 자동 멱등화 안 함).

### 4.3 `테니스_회원명부` 시즌시작순위

3장의 순서대로 1~16 기입, 명단 외 회원은 말번. 명부는 진실 소스 성격이므로 기입 전 최종 값을 유저에게 보여주고 승인받는다.

**소급 효과 주의**: `deriveLeagueForDate`는 `seasonStartRank`가 하나라도 생기면 "전원 흑기사(중립)" 체제에서 흑기사/흑장미 분할 체제로 바뀌고, `buildSinglesStandings`가 과거 모든 날짜에 이를 재적용하므로 **이미 기록된 단식 경기의 리그 역전 보너스 포인트가 소급 재계산된다**. 이는 의도된 동작이다(시드가 있어야 리그가 성립). 승인 게이트에서 기입 전/후 포인트 델타를 함께 보여준다 — 현재 앱에 단식 기록이 없으면 델타는 0이다.

## 5. 화면 — 분석 탭 (기존 records 탭 확장)

상단 **복식/단식 토글, 복식 기본**. 섹션 카드 구성:

| 섹션 | 복식 | 단식 |
|---|---|---|
| 개인성적 | 승/패/승률 랭킹 + 연도별 전적(2024·2025·2026·통산) | 동일 + **포인트** + 길로틴 순위표(기존 standings 흡수) |
| 파트너 케미 | 페어 조합별 판수/승/패/승률(최소 3판 노출), 선수 선택 시 파트너별 성적 | 없음 |
| 상대전적 | 개인 vs 개인 — 상대편에 섰던 모든 판 집계 | 개인 vs 개인 |
| 월별 흐름 | 선수별 월 승률 라인 그래프(2026~, 인라인 SVG) | 동일 |
| TB·베이글 | 타이브레이크 승률 랭킹, 베이글 준/받은 랭킹 | 동일 |
| 에이스/DF | 앱 기록분만 집계, "2026.8~ 기준" 캡션. 마이그레이션 빈값 행 제외 | 동일 |

- **포인트는 단식 전용**(1차 스펙 §4.5 "포인트는 단식 전용", `rankPoints.js`의 `format !== '단식' → 0` 가드). 복식 뷰에는 포인트 컬럼을 두지 않는다.
- 게스트는 랭킹 모집단에서 제외한다(케미·상대전적의 "상대"로는 표시). `league=미반영` 판(회원 3인 미만)도 같은 규칙 — 순위표 제외, 케미·상대전적 포함.
- 연도별 전적: 2024·2025는 레거시전적, 2026 이후는 로그 실계산, 통산은 합산.
- 단식은 2026 로우가 없으므로 당분간 연도별 전적 위주로 표시되고, 앱 기록이 쌓이면 자동으로 채워진다.
- 경기 중 상단 탭(참석명단·오늘 결과·개인기록·페어)과 대시보드 개인기록(roster) 탭은 **코드 변경 없음** — 단, roster 탭은 전체 로그를 읽으므로 마이그레이션 후 누적 수치(판수·TB·베이글·출석일)가 1~7월치만큼 커진다. 이는 의도된 결과다. "기존 표시를 지키려고" 날짜 필터를 추가하지 말 것.

## 6. 데이터 흐름

분석 탭 진입 시 `로그_테니스선수경기` 전체 + `테니스_레거시전적`을 읽어 클라이언트에서 지표 계산. 기존 records 탭이 쓰는 `TennisSync.getPlayerGames()` 패턴에 `getLegacyRecords()`를 추가한다. 사전집계 시트는 두지 않는다(현 규모 수백~수천 행이면 클라이언트 계산 충분).

지표 계산기는 `src/utils/tennis/` 순수 함수로 두고 화면과 분리한다(기존 `tennisStandings.js` 스타일).

## 7. 에러 처리

- 마이그레이션: 매핑 불가 이름·스코어 이상치는 dry-run에 전부 나열, 하나라도 미해결이면 적재하지 않는다. 배치 전송 실패 시 "legacy 행 존재 가드" 덕에 이어서 재실행해도 중복 적재되지 않는다(이미 적재된 경우 중단되므로 유저 판단 후 정리).
- 분석 탭: 시트 로드 실패 시 기존 records 탭의 빈 상태 처리 재사용. 레거시전적이 비어 있으면 연도별 섹션만 숨긴다.
- 에이스/DF 빈값 vs 0 구분을 파싱 단계에서 보존한다(숫자 강제 변환으로 빈값→0 오염 금지).

## 8. 테스트

- **지표 계산기 유닛테스트**: 케미·상대전적·월별 흐름·TB·베이글·포인트/연도별 합산 — 픽스처 로우 기반.
- **마이그레이션 변환기 유닛테스트**: 스코어→행 변환, 6-5 TB sentinel, 6-0 베이글 소급, 이름 매핑/게스트 판별, `determineCompetition` 투몽/미반영 판정, 빈값 aces/DF 보존, 날짜→game/match 구성(match_id 유일성).
- 렌더 검증 공백(기존 메모리 규칙): jsx 변경은 선언 순서 육안 + diff 정독 + 브라우저 스모크.
- 기존 테스트(746+) 전체 통과 유지. 풋살/축구는 테니스 격리 구조상 무영향이어야 한다.

## 9. 범위 밖 (이번에 안 함)

- 페어 닉네임 매핑(어닉·파국 등) — 필요해지면 추가.
- 2024·2025 로우데이터 복원, 월별 레거시 집계 적재.
- 연령대 분석 — **유저 확인 2026-08-10: 이번 범위 제외.** 명부에 연령 데이터 정리 후 별도 검토.
- 사전집계 시트, 마이그레이션 관리 UI.
